# 三处修复的工程复盘

这份文档记录"发现问题 → 定位根因 → 选择修法 → 验证"的完整过程。
代码在 `skill/`，验证在 `tests/`，两条命令即可复现：

```bash
python -m skill.cli demo      # 看行为差异
python -m skill.cli selftest  # 看断言是否成立
```

---

## 0. 共同根因：异常分支默认丢弃

三个 bug 表面无关，深挖是同一个设计问题：

> 插件的所有异常分支，默认动作都是"什么都不做"。

```text
陌生人不在许可名单  → ignored
会话状态是 paused   → skip
消息被撤回          → 没有监听点
发送结果不明        → 不处理，留在内存
静默时段            → 不回，也不排队
```

对插件来说这是合理取舍：它是能力提供者，不该替使用者做业务决策。
但对运营者来说这就是灾难 —— **沉默不可观测**。
你不知道今天有 3 个人找你而系统当成没看见。

所以修法的总原则只有一条：

> **把"什么都不做"从默认动作改成显式动作。**
> 每一条消息必须落在一个有名字的队列里，并且写入审计。

这条原则直接决定了三个模块的形状。

## 1. 陌生人消息被自动拦截

### 现象
粉丝第一次私信，机器人从不回，界面无提示，日志无记录。

### 定位方式
用一个陌生账号发 5 条不同性质的消息（打招呼、提问、夸奖、广告、仅图片），
观察插件行为：5 条全部无响应，且状态栏计数不变。
把同一账号加入许可名单后再发，立刻正常回复 —— 说明问题在准入判断，不在发送能力。

### 根因
两个语义被合并成一个布尔量：

```python
if sender in allowlist:
    reply()
else:
    pass   # ← "不该回" 和 "不知道怎么处理" 共用这个分支
```

`pass` 吞掉了信息。下游无法区分"这是垃圾"和"这是我没见过的情况"。

### 修法
拆成四值枚举，其中 `REVIEW` 专门承接"不确定"。

| 值 | 含义 | 后续 |
|---|---|---|
| `BLOCK` | 明确垃圾 | 丢弃 + 写日志（可统计） |
| `REVIEW` | 不确定 / 高风险 | 进人工队列（可见、可处理） |
| `PROBATION` | 陌生人但像真人 | 观察期内允许 1 条受控回复 |
| `NORMAL` | 老会话 | 常规回复 |

关键参数都在 `config/skill.toml` 的 `[dm.stranger]`：
日上限 8、字数 20、观察期 180 分钟。

### 为什么不干脆全放行
因为"能回"和"该回"是两件事。陌生人是骚扰与黑产的主要入口，
无条件放行会把账号从"漏消息"直接推到"被举报"。
分级准入是在两者之间取的可行点：**能回的受控回，不确定的留给人。**

### 验证
- `tests/test_stranger_gate.py::test_stranger_greeting_enters_probation`
- `tests/test_stranger_gate.py::test_never_silently_dropped`（15 条样本，断言每条都有 action + reason）
- `tests/test_pipeline.py::test_stranger_gets_reply`（端到端）

## 2. 会话暂停后永久停摆

### 现象
机器人整体在跑，但某个会话再也不回消息；重启插件才恢复。

### 定位方式
人为制造三类失败（页面切走、元素找不到、平台限流提示），
观察该会话后续消息的处理：全部被跳过，且没有任何重试记录。

### 根因
`paused` 是布尔量，不是状态。布尔量没有"恢复"这个转移：

```python
if paused:
    return   # 第一次异常 = 终点
```

### 修法
四态状态机：

```text
RUNNING ──失败──> SUSPENDED ──退避到点──> RECOVERING ──成功──> RUNNING
                       │                       │
                       └──── 超预算 / 平台限流 ──┴──> HALTED
```

三个设计决定值得说明：

**① 退避必须带抖动。**
固定 30s 重试的行为特征太强，比"重试 3 次"更容易被识别。抖动 ±25%。

**② 恢复要有预算。**
30 分钟最多 3 次。超过就 HALTED —— 因为风控场景下"重试成功"是小概率，
"重试导致升级处置"才是常态。

**③ 平台喊停和网络抖动必须区别对待。**

| 失败类型 | 典型错误文本 | 处理 |
|---|---|---|
| `TRANSIENT` | timeout / Element not found | 退避重试 |
| `PLATFORM_PAUSE` | 操作频繁 / 验证码 / 环境异常 | **立即 HALTED，不重试** |
| `AUTH` | 登录失效 / 401 | 立即 HALTED，等人扫码 |

把这三类混成一个 `except` 是这类系统最常见的错误。

### 开发中抓到的真实 bug
第一版 `begin_recovery()` 在 `RUNNING` 状态下也会记录一次恢复，
于是每次正常发送都扣预算，第 6 条消息就被误判停机。
是 `demo` 的输出对不上预期才发现的（原本应该有 4 条已回复，实际只有 3 条）。

修法：`RUNNING` 直接返回 `True`，不记预算。

对应测试：`test_running_send_does_not_consume_budget`。
这条测试是事后补的 —— 说明"先写 demo 再写测试"在这个项目里确实抓到了东西。

### 验证
- `tests/test_session_guard.py`（12 条，覆盖退避、封顶、预算、窗口滑动、三类失败）
- `tests/test_pipeline.py::test_paused_session_queues_instead_of_dropping`
- `demo` 第 10–13 行：页面抖动 → 退避中排队 → 平台限流 → 停机

## 3. 撤回与重复发送

### 现象
- 对方撤回消息后，机器人还是回了一句（对着空气说话）；
- 超时重发后，对方收到两遍同样的内容；
- 发送结果不明时，消息既没发出去也没留在队列里。

### 根因
发送侧没有幂等键，也没有"待发"这个中间态。

### 修法
- `PendingReply` 四态：`pending / sent / cancelled / unknown`；
- 撤回事件按 `(conv_id, msg_id)` 精确命中；
- 幂等键 = `sha1(会话 | 消息 | 正文)`，24h 窗口；
- 结果不明 → `unknown`，占住幂等键，**不重发**。

### 一个刻意的取舍
已发送的消息被撤回时，**只记录，不尝试删除**。

删除是更重的外部动作：要走另一套 UI 流程、失败率高、且"刚发完就删"本身
是个更可疑的行为特征。记录一笔、让运营者自己判断，性价比更高。

### 处理顺序的坑
`register()` 必须在所有"延后发送"判断**之前**调用。
第一版把它放在发送前一刻，结果静默时段的消息根本没有待发记录，
撤回事件命中不到 —— 表现为"深夜撤回的那条，第二天早上照发"。

现在 `pipeline.py` 里这一步有注释锁着，顺序不能动。

### 验证
- `tests/test_recall_guard.py`（7 条）
- `tests/test_pipeline.py::test_recall_cancels_deferred_reply`

## 4. 如果继续做，下一步是什么

按优先级：

1. **把审计日志接上可视化。** 现在 JSONL 只能 `tail`，看不出"今天漏了几条"。
2. **把陌生人准入从规则改成小模型分类。** 规则对变体话术的召回有限，
   但上模型要先把成本和延迟量出来。
3. **给 HALTED 做告警。** 现在停机只有日志，人不在电脑前就不知道。
4. **补真实环境的长周期数据。** 目前只有短期小规模测试，这是最大的空白。

不建议做的事：加更多自动发送能力。瓶颈不在"能不能发"，在"该不该发"。
