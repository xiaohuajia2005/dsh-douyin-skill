# DSH 抖音自动化 Skill

> 基于 DSH 框架的抖音 Agent Skill：监听私信、受控自动回复、点赞收藏、主动开口。
> 针对原版插件「陌生人消息被静默拦截」「会话暂停后永久停摆」两个缺陷做了二次开发。
> **面向社交平台的大模型自动交互 Demo，仅小号本地测试，不可商用。**

## 一、这个项目在做什么

DSH 的抖音类插件能驱动浏览器去看视频、回私信、发评论，但它是个"能力插件"，
不是"可靠系统"：所有异常分支的默认动作都是**丢弃**。

结果就是运营侧看到的现象 —— 今天没人找我 / 这个粉丝怎么不回我 / 机器人好像卡住了。
实际上消息来过，只是被吃掉了，而且没有任何日志能证明它来过。

本项目做两层改动，边界很清楚：

```text
插件层（patches/）   5 处原地改动 —— 修"怎么做"：分镜帧数、提示词、超时、消息指纹
适配层（skill/）     策略与护栏   —— 管"要不要做"：准入、状态机、幂等、主动开口
```

插件层的改动每次升级都要 rebase，所以只放"必须贴着 DOM 或提示词"的东西；
能抽象成策略的全部放适配层，因为那部分有单元测试。详见 [`docs/patches.md`](docs/patches.md)。

只在适配层做也不够 —— 本项目**不修改插件的浏览器驱动能力**，只接管它的决策，
把"丢弃"换成"排队并留痕"：

| | 原版 | 本项目 |
|---|---|---|
| 陌生人第一条私信 | 静默丢弃 | 观察期受控回复 / 进人工队列 |
| 会话异常后的消息 | 永久跳过 | 退避重试 → 超预算停机 → 消息留在队列 |
| 对方撤回消息后 | 照发不误 | 待发回复立即失效 |
| 发送结果不明 | 卡在内存里消失 | 标记结果不明，不重发，进核对队列 |
| 主动开口 | 只有一种语气 | 分「接话」「问候」两类，且先过护栏 |
| 异常发生时 | 无日志 | JSONL 审计，每条判定都有原因 |

**这套改动的验收标准只有一条：静默丢弃 = 0。**
演示脚本会把这个数字打出来（13 条模拟私信：原版 10 条静默丢弃 → 本版 0 条）。

## 二、四处二次修改（项目重点）

### 修复 1 · 陌生人消息被自动拦截

**现象**：粉丝第一次发私信，机器人从不回复，界面上也没有任何提示。

**根因**：插件把"要不要回"和"要不要看"合并成了一个二值判断，落在同一个 `ignored` 分支。
"我不确定该怎么处理"被迫退化为"当作没看见"。想回陌生人只能手动加许可名单，
既不能批量，也无法知道漏了谁。

**修法**：把过滤改成**分级准入**，给"不确定"单独留一条出路。

```text
文本 → 硬规则（链接/联系方式/复读/营销词）→ BLOCK      明确垃圾，丢弃但写日志
     → 转人工词（合作/投诉/报价）        → REVIEW     进人工队列，不自动回
     → 老会话（已关注/有历史）            → NORMAL     常规回复
     → 陌生人 + 打招呼/提问/夸一句        → PROBATION  观察期，允许 1 条受控短回复
     → 其余陌生人                        → REVIEW     进人工队列
```

观察期是有边界的能力，不是放开：日上限 8 条、单条 ≤20 字、比老会话更短、
不出现任何联系方式、过期 180 分钟回到复核。

代码：`skill/stranger_gate.py` · 测试：`tests/test_stranger_gate.py`（15 条，含"每条判定都必须有原因"的不变量测试）

### 修复 2 · 会话暂停后永久停摆

**现象**：某个粉丝的消息再也不回了，但机器人整体还在跑；重启插件才恢复。

**根因**：`paused` 被当成布尔开关而不是状态。布尔量没有"恢复"这个转移，
所以第一次异常就成了终点。

**修法**：换成显式状态机，四态三边。

```text
RUNNING ──失败──> SUSPENDED ──退避到点──> RECOVERING ──成功──> RUNNING
                       │                       │
                       └──── 超预算 / 平台限流 ──┴──> HALTED（等人处理）
```

三条约束比"重试"本身更重要：

1. **退避带抖动**（±25%）。固定 30 秒重试等于告诉平台"我是脚本"。
2. **恢复预算**：30 分钟内最多自动恢复 3 次，超了就是 HALTED。风控场景里越试越糟是常态。
3. **平台喊停就真停**：验证码 / 操作频繁 / 环境异常 → 直接 HALTED，一次都不重试。
   这类信号继续发只会升级处置（限流 → 封私信 → 封号）。

开发中这条被自己的演示脚本抓到过一次真实 bug：`begin_recovery()` 在正常发送时
也扣了一次恢复预算，导致第 6 条消息就被误判停机。这正是它需要单元测试的原因。

代码：`skill/session_guard.py` · 测试：`tests/test_session_guard.py`（12 条）

### 修复 3 · 撤回与重复发送

撤回、超时重发、结果不明，在发送侧是同一个问题：没有幂等键。

- 每条待发回复登记为 `PendingReply`，带 `pending / sent / cancelled / unknown` 四态；
- 撤回事件按 `(conv_id, msg_id)` 精确命中，发送前必须过这一关；
- 幂等键 = `sha1(会话 | 消息 | 正文)`，24h 窗口内只发一次；
- 结果不明一律置 `unknown` 且**不重发**，进人工核对。宁可少发一条，
  也不要让同一个粉丝收到两遍 —— 后者是举报的常见理由。

对已发送的消息，本项目**只记录不删除**。删除是更重的外部动作，失败率高且更容易触发风控。

代码：`skill/recall_guard.py` · 测试：`tests/test_recall_guard.py`（7 条）

### 修复 4 · 主动开口被当成一种语气

**现象**：主动发消息时，该接话的场合另起话题，该问候的场合又提起三天前的旧事。

**根因**：`reply()` 只有一个 `purpose = 'proactive'`，没有区分"对方最后一条还没回"
和"上一句是自己说的"。两种情况需要的开场完全不同，塞进同一个提示就会各错一半。

**修法**：拆成两类，注入不同段落。

| 类型 | 触发 | 提示要点 |
|---|---|---|
| `reply-pending` | 对方最后一条未回 | 自然接上它，可直接回应或顺着问一句；不另起话题、不复述原话、不提"上次" |
| `greet` | 上一句是自己说的 | 全新问候，问近况/吃饭没；不翻旧账，记忆里的事最多顺带问一件 |

**这条比前三条危险**：主动私信是单向发送，没有"对方先开口"这个天然授权，
被举报概率比回复高一个量级。所以适配层补了 [`skill/proactive_guard.py`](skill/proactive_guard.py)：

```text
非许可会话       → 禁止   对陌生人主动 = 骚扰，不留口子
连续 2 次没回应   → 禁止   单方面刷屏是最容易被举报的形态
静默时段         → 延后   到点再开口
日额度用完       → 延后   明天再说
会话冷却期内     → 延后   同一人不要反复开口
```

默认 `enabled = false`。测试：`tests/test_proactive_guard.py`（11 条）。

### 插件层的五处改动

上面四条改在适配层，另有 5 处直接改在插件源码上（`patches/`，可 `git apply -p1`）：

| 编号 | 文件 | 改动 | 解决什么 |
|---|---|---|---|
| P1 | `chat-agent.mjs` | 视频采样 4 帧 → 16 帧，交给分镜打包；本轮图片仍限 4 张；打包失败退化为前 4 帧 | 4 帧看不清"在演什么"，加帧不涨图片成本 |
| P2 | `chat-agent.mjs` | `reply()` 增加 `proactiveKind` / `proactiveLastText` | 主动开口分两类（即修复 4） |
| P3 | `chat-agent.mjs` | 长期记忆注入 20 条 → 10 条 | 省 token，也少犯"翻旧账" |
| P4 | `chat-browser.mjs` | 表情面板 4s→2s、分页 2s→1s、发送核对 10s→5s | 卡住时尽快失败，别把会话拖进暂停 |
| P5 | `chat-message.mjs` | 分享卡片指纹只取稳定身份（`videoId` 等 4 个字段） | 封面异步加载导致指纹变化，被自己误判成"消息被改动" |

**P5 是"会话暂停"里最难查的一类**：不是网络问题，是程序把自己判成了异常。
表现是"别人的消息都正常，只有带分享卡片的那条一直不回"。

完整复盘（含风险与验证边界）：[`docs/patches.md`](docs/patches.md)。

## 三、实现功能

| 能力 | 状态 | 说明 |
|---|---|---|
| 刷视频（自主观看） | ✅ 可用 | 每日 30 分钟上限，静默时段不跑，音频理解默认关闭 |
| 私信监听 | ✅ 可用 | 适配层接管判定，所有消息都有明确去向 |
| 私信自动回复 | ⚠️ 受限 | 见下方"局限"：只能在插件已打开的网页会话内发送 |
| 主动开口 | ⚠️ 默认关闭 | 分「接话 / 问候」两类，先过护栏：仅限许可会话、日 3 次、6h 冷却、2 次未回应即停 |
| 点赞 / 收藏 | ✅ 可用 | 日上限 20 / 5，且要求"看完再互动" |
| 群聊回复 | ✅ 可用 | 仅回被 @ 或叫到设定昵称的消息，普通群消息不回 |
| 视频分镜 | ✅ 已调优 | 采样 4 帧 → 16 帧打包成一张分镜图，本轮图片总数仍限 4 |
| 发表评论 | ⚠️ 默认关闭 | 原版的公开评论发布未通过真实环境验证，代码里默认 `enabled = false` |
| 撤回适配 | ✅ 可用 | 待发回复失效，已发送仅记录 |
| 审计日志 | ✅ 可用 | 决策落 JSONL，不含正文原文，只存哈希与判定 |

## 四、处理链

一条私信进来之后的固定路径。顺序不能调换：

```text
撤回事件          先于一切。撤回的消息不该有任何后续动作
  ↓
陌生人准入        BLOCK / REVIEW / PROBATION / NORMAL
  ↓
登记待发          ★ 必须在所有"延后发送"判断之前，否则撤回命不中
  ↓
静默时段          到点不发 → 待发队列（不是丢弃）
  ↓
会话状态机        退避/停机时 → 排队（不是丢弃）
  ↓
幂等去重          同一 (会话, 消息, 正文) 只发一次
  ↓
发送              成功 / 失败都落审计
```

**每一步的默认动作都是"留在队列里"，这是对原版最根本的一处改动。**

## 七、配置说明

唯一事实来源是 `config/skill.toml`。所有阈值默认比平台更保守，注释里写了理由。

### 私信侧

| 键 | 默认 | 含义 / 为什么这么设 |
|---|---|---|
| `dm.reply_max_chars` | `25` | 老会话回复字数上限。长回复是成本黑洞，也是人设崩塌的第一信号 |
| `dm.quiet_hours` | `["00:00","08:00"]` | 静默时段。凌晨发消息是机器人最显眼的特征之一 |
| `dm.handoff_keywords` | 合作/报价/投诉/律师… | 命中即转人工，绝不自动回 |
| `dm.never_say` | 微信/QQ/链接/电话… | 回复里出现即判定站外引流，直接丢弃重写。**这是私信被封的第一大原因** |

### 陌生人准入（修复 1）

| 键 | 默认 | 含义 |
|---|---|---|
| `dm.stranger.enable` | `true` | 关闭也不回到"静默丢弃"，仍然进人工队列 |
| `dm.stranger.daily_reply_limit` | `8` | 陌生人自动回复日上限，远低于老会话 |
| `dm.stranger.max_chars` | `20` | 比老会话更短 |
| `dm.stranger.probation_ttl_minutes` | `180` | 观察期时长，过期回到复核 |

### 会话状态机（修复 2）

| 键 | 默认 | 含义 |
|---|---|---|
| `session.max_consecutive_failures` | `3` | 连续失败几次判定异常 |
| `session.backoff_base_seconds` | `30` | 首次退避 30s，之后指数增长 |
| `session.backoff_cap_seconds` | `600` | 退避封顶 10 分钟 |
| `session.jitter_ratio` | `0.25` | 抖动 ±25%，避免固定节奏被识别 |
| `session.max_resumes_per_window` | `3` | 30 分钟内最多自动恢复 3 次 |
| `session.halt_on_platform_pause` | `true` | 平台侧限流/验证码直接停机，不重试 |

### 撤回与幂等（修复 3）

| 键 | 默认 | 含义 |
|---|---|---|
| `recall.pending_ttl_seconds` | `600` | 待发回复 10 分钟未发出即作废 |
| `recall.dedupe_seconds` | `86400` | 同一条消息 24h 内只回一次 |
| `recall.resend_on_unknown` | `false` | 结果不明不重发，宁可少发不可重发 |

### 主动开口（修复 4）

| 键 | 默认 | 含义 |
|---|---|---|
| `dm.proactive.enabled` | `false` | 总开关。主动私信是风控最重的动作，默认不开 |
| `dm.proactive.daily_limit` | `3` | 全账号每日上限 |
| `dm.proactive.per_conversation_cooldown_minutes` | `360` | 同一会话两次主动至少隔 6 小时 |
| `dm.proactive.max_unanswered` | `2` | 连续 2 次主动没得到回应 → 对该会话停止主动 |
| `dm.proactive.only_permitted` | `true` | 只对许可会话开口；对陌生人主动 = 骚扰 |
| `dm.proactive.quiet_hours` | `["00:00","08:00"]` | 静默时段 |

### 互动与模型

| 键 | 默认 | 含义 |
|---|---|---|
| `interaction.like_daily_limit` | `20` | 点赞日上限 |

## 八、风险备注

本项目驱动的是**抖音网页版**，属于用户协议明确禁止的自动化行为。
下面的风险不会因为代码写得好而消失，只会因为参数保守而降低概率。

| 编号 | 风险 | 级别 | 应对 |
|---|---|---|---|
| R1 | 自动化操作被识别，私信功能被限制 | 🔴 | 灰度放量；出现验证码立刻停机 72h |
| R2 | 账号被封（永久） | 🔴 | **只用小号**，不与主号同设备、同网段、同手机号 |
| R3 | 站外引流判定（回复里含联系方式） | 🔴 | `never_say` 硬拦 + 发送前二次校验 |
| R4 | 评论被判垃圾/折叠 | 🟠 | 日上限 2 条，模板化，同作品去重 |
| R5 | 同设备关联导致主号被连累 | 🔴 | 小号独立浏览器 profile，独立时段 |
| R6 | 回复重复 / 对方收到两遍 | 🟠 | 幂等键 + 结果不明不重发 |
| R7 | 平台接口变更导致脚本失效 | 🟠 | 状态机 HALTED 而不是死循环；失败可见 |
| R8 | 深夜自动回复打扰用户被举报 | 🟡 | 静默时段 00:00–08:00 |
| R9 | 陌生人批量回复被判定骚扰 | 🟠 | 观察期 + 日上限 8 条 |
| R10 | 法律与平台规则风险 | 🔴 | 仅本地测试，不对外提供服务，不商用 |

**灰度日程**（不要跳步）：

| 阶段 | 天数 | 开放 | 回退条件 |
|---|---|---|---|
| 只看 | 1–3 | 视频观看 | 出现验证码 / 播放不推进 |
| 只回 | 4–7 | 观看 + 私信 | 回复重复 / 发送结果不明 |
| 试评 | 8–14 | 加上评论 | 评论被折叠 / 收到违规提示 |
| 放量 | 15+ | 全部 | 任何账号异常，回退一档并停 72h |

> ⚠️ **请只用小号。** 主号一旦因同设备关联被封，申诉成功率极低。
> 本项目不提供、也不建议任何绕过平台风控的手段。

完整风险矩阵见 [`docs/risk.md`](docs/risk.md)。

## 九、局限（如实说明）

这部分比功能列表更重要，因为它决定了这个项目**能用来做什么、不能用来做什么**。

1. **只在小号上做过本地测试。** 没有多账号、多设备、长周期（>14 天）的稳定性数据。
   上表里的所有参数是小规模试出来的保守值，不是调优结果。

2. **受抖音网页版接口限制。**
   本项目不调用抖音开放平台 API，全部依赖网页 DOM。这意味着：
   - 页面改版就失效，且失效方式是"找不到元素"而不是"报错退出"；
   - 只能发送到插件已经打开的会话里，不能主动发起会话；
   - 私信只能覆盖插件运行期间的新消息，历史消息不补答；
   - 发送成功率、延迟都不受本项目控制。

3. **有风控封号风险，且无法消除。**
   网页自动化的行为特征（节奏规律、无鼠标轨迹、停留时间方差小）是结构性的。
   参数只能降低概率，不能消除。**代码里没有留任何绕过风控的口子，也不打算留。**

4. **自动评论是原版唯一没通过真实环境验证的能力。**
   原版文档把"公开评论发布确认"列在未验证项，因此本项目默认关闭
   （`comment.enabled = false`）。评论模板与离线体检工具是齐的，但我不建议在验证前打开。

5. **插件改动基于 1.4.6，尚未 rebase 到上游 1.4.7。**
   上游 1.4.7（2026-11-12）已独立修了一批同类问题，其中至少
   "不因附件多而暂停整段聊天"和撤回处理与本项目的 P1 / 修复 3 重叠。
   继续用 1.4.6 意味着放弃上游这些修复；升到 1.4.7 则需要逐条确认 P1–P5 是否还有必要。
   **这件事没做，所以不声称做了。**

6. **两个改动没有 diff。**
   `chat-service.mjs` 与 `memory-star.mjs` 被改过但没留 `.bak` 基线，
   因此无法产出可靠 patch，只能靠重新安装上游文件来对比。记录见 [`patches/README.md`](patches/README.md)。

7. **P1 与 P4 的效果无法离线验证。**
   分镜 16 帧"是否比分 4 帧更看得懂"、超时收紧后表情发送成功率是否下降，
   都必须在真实环境跑够样本才能下结论。本地只做了结构回归（帧数上限、退化路径、计数）。

8. **不是商用方案。**
   没有多租户、没有权限隔离、没有 SLA、没有内容审核兜底。
   它是个技术 Demo，用来验证"给社交平台加一层可靠的交互决策层"这件事怎么做。

9. **合规边界。**
   自动化操作社交平台通常违反其用户协议；批量回复陌生人可能被认定为骚扰；
   抓取他人内容涉及隐私。**仅限个人小号、本地、自娱自乐。**

## 十二、设计取舍（面试常被问的四点）

**为什么不做成"全自动"？**
因为全自动在这里等于"无条件发送"，而风控场景下无条件发送是负收益。
真正稀缺的不是发送能力，是**知道什么时候不发送**。整套代码里"沉默"和"排队"
都是显式动作，不是异常。

**为什么用状态机而不是重试装饰器？**
重试装饰器只能表达"再试几次然后放弃"，表达不了"平台让我停"和"我自己恢复太多次了该停"
这两种完全不同的失败语义。后者的正确处理是停下来等人，不是继续试。

**为什么既改源码又加适配层？**
因为两类问题的正确归属不同：分镜帧数、提示词措辞、DOM 超时、消息指纹，
这些**必须贴着实现**，只能改源码；准入、状态机、幂等、主动开口资格，
这些是纯策略，放适配层才有单元测试。源码改动每次升级都要 rebase，
所以能抽出来的一律抽出来 —— 这也是为什么插件层只有 5 处，而适配层有 4 个模块。

**为什么零依赖？**
这个项目最需要被验证的部分（判定逻辑、状态转移、幂等）全是纯函数，
不该为了跑测试去装 pytest。用 `unittest` + `tomllib`，任何一台机器克隆下来就能
`python -m skill.cli selftest`，这对一个"给别人看的 Demo"很重要。
